# v1.3 接收助手与断点续传 — 设计文档

- 日期：2026-08-06
- 状态：待评审
- 目标版本：1.3
- 基线：`origin/main` @ `fb03df9`（v1.2.1），分支 `codex/feature-v1.3-receive-assistant`

## 背景与动机

v1.2 聚焦 OPP 通用推送，移除了 1.0 的双端互联（含断点续传）。OPP 固有限制为：明文、无续传、接收端失败即丢弃。README「未来开发点」曾列出"极简接收助手模式"（私有分片协议 + Offset 续传，与 OPP 并存、未装助手自动回退），当时明确暂不实现。

v1.3 把该方向落地，同时补齐 GUI 长列表滚轮体验与队列管理能力。接收端平台确定为 **Windows**，与发送端共用 .NET 8 技术栈。

## 目标

1. **GUI 滚轮滑动**：任务队列、传输记录、日志、设备列表支持"悬停即滚"（无需先聚焦）；日志自动跟随底部、用户上翻时暂停跟随、翻回底部恢复；日志上限 500 → 2000 行。
2. **接收助手（btrecv）**：CLI 内核 + 极简 GUI 壳，注册自定义 RFCOMM 服务接收文件，支持自动接收 / 每次询问两种模式。
3. **断点续传 + 真正的传输队列**：私有分片协议（明文 v1，Offset 续传）；队列任务支持单独 暂停/继续/移除/重试；助手模式断线重试=重连+从上次 ACK 偏移续传。简单 SHA-256 校验保证完整性。
4. **引导**：自包含单文件 `btrecv`（CLI/GUI 双形态）可通过 OPP 先推给目标 Windows 电脑，解压即用；另保留 framework-dependent 发布配置作为小体积备选。

## 非目标（v1.3 明确不做）

- 传输加密（明文 v1；链路层加密仍可用 Windows 侧配置）
- 发送端队列跨重启持久化（偏移仅存内存；接收端 `.btpart` 天然跨重启存活）
- 接收端数据库（仅内存会话列表 + 磁盘半成品/元数据）
- Android / iOS 接收端（仅 Windows）
- 同一接收端多传输并发（同时只处理一个，忙回 BUSY）
- 全文件哈希的接收端增量状态持久化（完成时一次性校验）

## 私有协议 v1（明文）

### 服务发现

- 固定随机 UUID（实现时生成常量）注册自定义 RFCOMM 服务；发送端 SDP 查询该 UUID 判断"助手可用"
- 发送端出站 RFCOMM 仍要求已配对（Windows 栈限制），复用现有配对流程

### 帧格式

- 长度前缀（4 字节小端）+ 消息类型（1 字节）+ 载荷
- 全明文；无 OBEX 4GB 头约束，单文件上限受磁盘与传输时长限制

### 消息类型

| 消息 | 方向 | 作用 |
|---|---|---|
| HELLO | 发送→接收 | transferId、fileName、fileSize、chunkSize、expectedSha256 |
| OFFER | 接收→发送 | 状态（ACCEPT / BUSY / REJECT）+ 本端已落盘偏移量 |
| DATA | 发送→接收 | 分片数据（默认 32768，复用 `OppChunkSize`） |
| ACK | 接收→发送 | 已持久化偏移量（续传检查点） |
| DONE | 接收→发送 | 完成确认（含校验结果） |
| CANCEL | 双向 | 暂停/取消；接收端保留半成品 |
| ERROR | 双向 | 错误码（busy / disk_full / mismatch / hash_mismatch 等） |

### 握手与续传流程

1. 发送端连接自定义服务，发送 HELLO（transferId 为队列任务 GUID，发送前用 `FileChecksum` 预计算 SHA-256）
2. 接收端查 `<name>.btmeta`：同 transferId 且 fileSize 一致 → OFFER(ACCEPT, offset=N)；有半成品但元数据不匹配 → OFFER(ACCEPT, offset=0)；忙 → OFFER(BUSY)
3. 发送端从偏移 N 打开文件继续流式发送 DATA；接收端追加写入 `.btpart`，每分片落盘后回 ACK(offset)
4. 全部发完 → 接收端对完整文件算 SHA-256 与 expectedSha256 比对 → DONE(ok) / ERROR(hash_mismatch)
5. 成功：`.btpart` 改名为正式文件（重名自动 `name (1).ext`），清理 `.btmeta`；失败(hash_mismatch)：删除半成品与元数据，发送端标记失败（原因"校验失败"），重试时从 0 整传

### 暂停 / 取消 / 忙 / 断线自愈

- 暂停：发送端停止发送并断开（或发 CANCEL）；接收端保留 `.btpart` + `.btmeta`；继续时重连握手从偏移续传
- 取消/移除：发送端发 CANCEL（或直接断开）；接收端保留半成品（下次同 transferId 可续），残留由启动时 7 天过期清理兜底
- 忙：接收端同时只处理一个传输，忙回 BUSY；发送端任务保持排队，按现有 `OppRetryPolicy` 指数退避重试
- 断线：助手模式重试 = 重连 + 从上次 ACK 偏移继续，而非从头重发

## 发送端设计

### 模式解析

- 全局配置 `TransferMode: auto | assistant | opp`（默认 auto）
- auto：连接前 SDP 探测助手 UUID → 命中走私有协议，否则回退 OPP
- 设备列表：探测结果缓存，显示「助手」徽标

### 队列升级（OppSendQueue）

- 状态机增加 `Paused`；每任务支持 暂停 / 继续 / 移除 / 重试（在现有"取消全部、单任务重发"基础上补齐）
- 任务增加通道信息（OPP / 助手），GUI 队列显示通道列
- 助手模式重试沿用指数退避但每次从 ACK 偏移续传；OPP 模式行为完全不变

### 发送服务与记录

- Core `AssistantClient` 负责协议收发；GUI 侧新增薄封装 `AssistantPushService`，复用现有预处理（文本→.txt、文件夹→zip、剪贴板、拖放）
- 事件/进度/记录复用现有 EventBus 与 SQLite：`channel=assistant`、`direction=send`，记录表无需迁移

### GUI 交互

- 队列每行 暂停/继续/移除/重试 按钮或右键菜单
- 状态栏显示「助手模式 · 已传 xx% · 续传点」
- 滚轮：`PreviewMouseWheel` 统一处理（GUI 工程内，不进 Core）——悬停即滚、无需聚焦；日志自动跟随、上翻暂停跟随、翻回底部恢复；日志上限 2000

### CLI（btcli）

- 现有 `opp-send-*` 命令增加 `--mode auto|assistant|opp`（默认 `opp`，旧脚本行为不变）
- 新增 `btcli detect <地址>`：探测助手是否在线
- 新增 `btcli package-receiver`：调用发布脚本产出 btrecv 包

## 接收端设计（btrecv）

### 命令

- `btrecv` / `btrecv gui`：启动极简 GUI 壳
- `btrecv run [--dir 保存目录] [--ask]`：CLI 内核运行；默认自动接收，`--ask` 时控制台逐次提示接受/拒绝
- `--help` / `--version`

### GUI 壳（WPF 小窗）

- 状态栏（监听中/忙）
- 当前传输：文件名、进度、速率
- 本会话完成列表
- 设置区：保存目录、自动/询问切换；询问模式下每条传输带「接受/拒绝」按钮
- 保持极简：不加托盘、不加数据库

### 存储布局

- 默认目录 `%USERPROFILE%\Downloads\BluetoothReceive`
- 接收中：`<文件名>.btpart` + 同名 `.btmeta`（transferId、fileSize、创建时间）
- 完成后改名正式文件名；重名自动 `name (1).ext`
- 启动时清理超过 7 天的残留 `.btpart` / `.btmeta`

### 生命周期与并发

- 助手必须保持运行才能收；关闭即停止监听（README 说明）
- 同时只处理一个传输，忙回 BUSY

## 引导包与发布

1. 发送端先用 OPP 推送 `btrecv` 包（自包含单文件或 zip）
2. 对端解压、运行 `btrecv`（自包含无需装运行时）
3. 发送端扫描 → SDP 探测到助手 → 设备列表「助手」徽标 → 自动走私有通道；探测不到继续用 OPP
- GUI「发送」区加「打包接收助手」按钮（产出后可直接加入队列推送）；CLI 对应 `btcli package-receiver`

## 错误处理汇总

| 场景 | 处理 |
|---|---|
| 接收端忙 | OFFER(BUSY)，发送端退避重试 |
| 传输中断线 | 助手模式重连续传；OPP 模式维持现有整传重试 |
| 磁盘满 / 权限不足 | ERROR(disk_full)，任务失败并给出原因 |
| 元数据不匹配 | OFFER(offset=0)，整传重来 |
| 哈希不匹配 | ERROR(hash_mismatch)，接收端清半成品，任务失败可重试 |
| 文件名冲突 | 接收端自动 `name (1).ext` |
| 助手未装/不在线 | SDP 探测不到 → 回退 OPP（auto 模式）或按强制模式报错 |

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| Windows RFCOMM 服务端在部分栈上注册不稳定 | 真机矩阵覆盖；SDP 探测失败自动回退 OPP，不阻塞主链路 |
| 哈希校验增加完成时全文件读取 | 只读一次；发送端预计算与记录复用 |
| 队列状态机改动引入回归 | 状态机单测 + 存量 89 测试回归 |
| 自包含包体积大、蓝牙推送慢 | 一次性引导可接受；备选 framework-dependent 配置 |

## 实施顺序建议（writing-plans 细化）

1. Core：协议帧/消息 + 内存传输抽象（可先于蓝牙落地单测）
2. Core：AssistantClient / AssistantServer + 续传与哈希校验
3. Receiver 项目：CLI 内核 → GUI 壳 → 发布脚本
4. 发送端：模式解析 + AssistantPushService + 队列升级 + GUI/CLI 接线
5. GUI 滚轮与日志优化
6. 测试补齐 + 真机验收

## 附录 A（2026-08-07 增补）：完整 GUI 内置接收助手

- 动机：两台主机都安装完整 GUI 时可直接互传，无需单独运行 btrecv。
- 设计：主窗口「接收助手」面板——开始/停止监听开关、当前传输进度、本会话完成列表、保存目录（默认 下载\BluetoothReceive，可改）、每次接收前询问复选框；监听开启时注册自定义 RFCOMM 服务（复用 Core 的 `AsstRfcommService`/`AssistantServer`/`AsstFileSink`）；接收完成写入同一 SQLite（direction=recv、channel=assistant）。
- 默认行为：启动默认不监听，手动点「开始监听」；同一台机器上完整 GUI 与 btrecv 二选一运行（同一服务 UUID）。
- 产物策略：btrecv 全形态保留（最小引导场景）；完整 GUI 与 btrecv 可互发、互收。
